# Robustness Backport Register

> **Scope.** Tracks candidate hardening items for completed Stage B–F surfaces (and Stage G surfaces that have already landed at file scope). Each row is a focused, self-contained robustness improvement — no architecture re-litigation, no behavior changes beyond closing an attack / error class. Items are ranked by `Exploitability × inverse(Cost)` and worked in small "robustness packets" (interface / type locks → state / admin slot cleanup → revert-surface + negative tests → cross-stage docs reconciliation) so completed stages stay shippable while safety compounds.
>
> **Process.** Items enter at status `Open` via audit (planned or opportunistic); move to `Scoped` once the §8e.1-shape change is sized; `In-flight` once a sub-step is authored; `Closed` once the commit lands. Closure rows record the commit hash + a one-line delta describing what attack / error class was removed.
>
> **Out of scope.** Architecture decisions (fee split, factory pattern, authorizer model, vault isolation), spec-level token / pool selections, and emission-curve constants. These are sealed at their respective stage decisions and only reopen via explicit chat-level discussion.

## Hardening classes

- **Input-domain hardening** — replace loose params with enums / value objects; restrict accepted shapes at the public surface.
- **Allowlist hardening** — explicit accepted-token / accepted-type domains; fail closed, never best-effort.
- **Strict-equality vs tolerance audit** — enforce exactness where exact is safer (anti-spam fees, fee splits, immutable invariants); reject "epsilon" tolerance unless physically required.
- **Admin-path hardening** — one-shot setters, burn-after-init, no lingering privileged slots; admin slot zeroed atomically with module-set.
- **Storage-class hardening** — promote storage variables to `immutable` / `constant` when never reassigned after construction; locks slot type at deploy, removes storage-write attack surface, eliminates one SLOAD per read. Eligible for value types and (since Solidity 0.8.21) reference types like `string` / `bytes`.
- **Epoch / boundary determinism** — no mid-interval state surprises; epoch transitions read-once, written-once.
- **Error taxonomy** — custom errors mapped 1:1 to guard classes; no `require(string)`, no plain `revert()`.
- **Invariant tests** — unauthorized caller, invalid type / token, under / overpay, reentrancy, stale callbacks, malformed payloads — every guard has at least one failing-path test.
- **Cross-stage interface** — when an interface is extended in-place across stages, dependent mocks / tests must mirror the change in the same commit; never silent drift.
- **External-call & type-cast safety** — wrap external ERC20 movements in `SafeERC20.safeTransfer` / `safeTransferFrom`; replace narrowing typecasts (`uint256(int256_var)`, `int256(uint256_var)`, `address(uint160(...))`) with typed constants, signed-add helpers, and labeled `makeAddr` synthetic addresses. Fix `forge-lint` warnings at source — zero `forge-lint: disable-next-line` suppressions in production or test code.
- **Test-fixture isolation** — fork-test fixtures must not communicate with deploy scripts through process-global state (`vm.setEnv` → `vm.envAddress`); configuration passes as explicit arguments so Foundry's contract-level parallelism cannot race. Until the RB-006 migration lands, serialized invocation (`--threads 1`) is the enforced posture (D36 / F-D11 / PB-D13).
- **Contract-identity verification** — a contract whose behavioral identity matters at a call site must expose a positive, cheap-to-read identity marker (constant discriminant, version value, or ERC-165 flag), and the call site must assert it before relying on implementation-specific behavior. A Solidity contract-type cast is a compile-time annotation with no runtime check: when a fork and its upstream share a selector, the cast dispatches against whatever the address actually holds and silently executes the other implementation's body. ABI-compatible substitutes must fail loudly, never take a different code path in silence. The assertion's POSITION is part of the rule rather than an implementation detail of it: a marker checked after the operation it should gate leaves that operation's own failure as the sole observable, so the named error the check exists to produce is never reached, and where the operation is itself unsupported on the substitute the check cannot fire at all (PB-D27 (ix) / E-D16 / RB-008; ordering half PB-D52 (iv) / RB-016).
- **Deployment-limit verification** — an artifact's deployed size is a chain-imposed constraint the local toolchain never applies: forge does not enforce EIP-170 in simulation, so a contract too large to deploy to any chain executes normally in every unit and fork test, and size is invisible to the whole pipeline by construction. Every artifact the project deploys is asserted against the limit by a standing test that names each artifact explicitly, because no unscoped `forge build --sizes` invocation can serve — test contracts and deploy scripts legitimately exceed the limit and forge exposes no per-contract exclusion. Where two compiler profiles emit the same contract to different out directories, every consumer names the intended artifact path explicitly rather than relying on default resolution (PB-D32 (x) / PB-D37 / RB-009).
- **Environment-scope isolation** — configuration that selects between deployment environments activates on explicit intent, never on incidental key presence, and a file the toolchain auto-loads is shared by every invocation regardless of target chain. An override resolver keyed on existence alone silently redirects one environment's literals whenever the other environment's values are present, and a passthrough default makes a populated map indistinguishable from an empty one until a value is dereferenced. Per-chain configuration sets are complete and self-contained rather than overlays with precedence, and the active set carries a marker that consumers assert before running (PB-D35 (ix) / PB-D36 / RB-010).
- **Deployment sequencing** — a deployment step whose precondition is produced by the protocol's own runtime cannot be ordered by deploy-time reasoning alone: where a contract's initialization consumes a token the protocol only mints past a block-height gate, that step belongs after the gate regardless of where the contract is created, and no one-sided inflow path substitutes when the path is itself gated by `withInitializedPool`. Test harnesses conceal this class by construction, since `vm.roll` and cheatcode balances satisfy the precondition for free, so the ordering is asserted in the runbook and by a pre-broadcast check rather than discovered on a chain whose sequence runs once (PB-D41 (ix) / RB-011).
- **Indirection-level typing** — where a mapping resolves one address domain into another, an argument drawn from its domain and an argument drawn from its codomain are the same Solidity type, and no cast, interface, or compiler check distinguishes them; a setter accepting either admits wrong-level entries in silence. The failure hides at both ends: the write reverts nothing and emits its ordinary event, and the read path discards the dead entry through a routine zero-gate rather than an error, so the sole observable is a downstream value that is quietly too small. Governance setters over resolved domains assert positive membership at admission — the argument is something that currently resolves, or is currently resolved to, as the level requires — rather than trusting the type, and the assertion lands in the wiring script and the operator runbook as well as in the contract, because the operator choosing the seed is where the level is actually decided (PB-D42 (iii) / PB-D43 (vi) / RB-012).
- **Cross-authority coupling** — a gate that is conjunctive over facts owned by different authorities inherits the loosest permission model for opening the gap and the strictest for closing it: where one precondition is set by a permissionless or bonded path and another by a governance-only path, the fast path sets how often the two disagree and the slow path sets how long each disagreement lasts, while no participant owns the interval between them. The failure is diagnostically displaced rather than merely deferred — the gate reverts on whichever conjunct it happens to test first, so the operator reads an error describing the symptom while the cause sits in a registry that error never names. Either the authorities are coupled, so admission on one side asserts the corresponding fact on the other, or the gap is made observable through a failure specific enough to name the missing act and a standing check that the two sets agree; carrying the duty in a runbook alone leaves it owned by whoever remembers (PB-D43 (vii) / RB-013).
- **Deployment-record completeness** — a deploy script that creates more contracts than it emits addresses for leaves live code no one can reach: the contracts exist, consumed gas, and are absent from every artifact the project keeps. Whether that is recoverable is a matter of topology rather than of effort — an unrecorded deployment can be re-derived only when some recorded on-chain object points back at it, as an ERC-4626 vault points at its asset, and cannot when the only reference runs the other way or when the artifact class admits no enumeration. Deterministic addressing is a fallback rather than a guarantee: it requires knowing the creation ordering, and it evaporates under CREATE2 or CREATE3, where the address turns on a salt instead of a walkable sequence. Every script therefore emits an address for every contract it creates, keyed so that no two kinds of artifact share one namespace, and those addresses land in the chain's committed deployment record rather than in an environment file the repository does not track (PB-D42 / PB-D47 (viii) / RB-014).
- **Degenerate-parameter scoping** — a derivation sound only because some parameter takes a degenerate value in the current environment records that dependence where the derivation sits, because the collapsed form and the general form become textually indistinguishable the moment the parameter drops out of the arithmetic. Setting every price to one turns `weight_i * V / P_i` into `weight_i * V`, and the surviving expression carries no trace of the division that cancelled, so no reader recovers the precondition from the code, nor from a lock that reasons its way to the right answer for a reason true only of the chain in front of it. The hazard is not that the simplification is wrong — on a chain of fabricated 1:1 stubs a flat unit price is the only price that exists, and the collapsed rule is the only coherent one — but that the artifact a later author consults as authority states the collapsed rule and then stops, so a testnet accommodation crosses a chain boundary without anyone deciding that it should. Every environment-conditional simplification therefore names its condition at the point of derivation rather than in surrounding prose, and the crossing is a gated obligation with its own assertion rather than an inheritance (PB-D46 (iv) / PB-D51 / RB-015).
- **Irreversible-authority binding** — a one-shot setter that burns its own admin in the same call converts a configuration mistake into a permanent capability loss, so its target belongs in a locked decision and its transaction belongs in a runbook with a simulation ahead of it, rather than being inferred at broadcast time from a document written before the alternatives existed. The seat succeeds and emits normally whatever address it is given; the loss is observable only later, when some function the slot gates is needed and no caller on earth can reach it, which places an unbounded delay between the mistake and its only symptom. A target is admissible only if it holds a call path to EVERY function the slot gates — a contract whose dispatch is a fixed enumeration of proposal types reaches none of them and would therefore delete the levers it appears to delegate. The rule generalises past any one slot: where no rotation path exists anywhere in the system, correctness of the binding cannot be established after the fact by reading state, so it must be established before the send by exercising the guards themselves, an `eth_call` from the intended sender rather than a derivation of a private admin slot (PB-D61 / RB-017; sibling one-shot seals at C-D11 and PB-D11).
- **Build-profile isolation** — two compiler profiles that write one shared derived-state store make build ORDER a silent input to every later lookup. A profile may redirect its artifact directory and still share `cache_path`, so source files the profiles have in common are recorded by whichever build ran last, and a tool resolving an artifact by name and compiler version then fails against a profile that did in fact compile it. The failure names the VERSION rather than the ordering, and the artifact it reports missing is present on disk throughout, so the obvious first diagnostic confirms the wrong hypothesis. A profile that overrides `out` overrides `cache_path` with it; where the sharing is kept, the ordering is made explicit at every consumer that depends on it (PB-D67 (ix) / RB-018).
- **Attested-obligation verification** — an on-chain flag recording that some party WILL perform a manual action is a claim about the future rather than a fact, and nothing on chain checks whether it was honoured; where such a flag gates value flow, pair it with an expiry that forces conscious renewal, or with a marker the action itself writes, so the promise and the payout cannot run on independent clocks.
