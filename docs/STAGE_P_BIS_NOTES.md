## PB-D1 — Sepolia is the live-broadcast target (closes the P-D1 live-target deferral; user-adjudicated 2026-07-11)

### PB11 — an em-dash (U+2014) is invalid inside a Solidity string literal — solc 0.8.26 rejects it (invalid-character-in-string-literal, observed as Error 8936); §10's em-dash house style is comments / NatSpec only

Caught at PB2.11b-vi, the face-3 compile of `test/fork/WK18ThinVenuePumpSim.t.sol`: an assertion-message string carried a copy-pasted em-dash and solc 0.8.26 rejected the file at parse with the invalid-character-in-string-literal error (observed as Error 8936). A plain `"..."` string literal admits only printable ASCII plus the defined escape set — U+2014 is representable only in a `unicode"..."` literal or via a `\u2014` escape, neither wanted in a message that compiles into bytecode. §10's em-dash convention is a PROSE house style: it governs comments, NatSpec, docs, and commit messages (UTF-8 to solc, or ignored), but any string that reaches the compiler as a literal — revert reasons, `require` / `assert` / `revert` messages, forge assertion-message arguments, event strings — must be ASCII.

**Rule.** When prose is copied into a Solidity string literal, convert every em-dash to ASCII (`-`, `--`, or reword); after a Solidity edit that pasted prose, grep the diff for U+2014 inside double-quotes before compiling. §10 stops at the quote mark.

## PB-D26 — PB3.4d2c amendment to PB-D20 (i): the stub override must reorder, not only re-address — an unconditional ascending sort with lockstep weight permutation (user-adjudicated 2026-07-25; PB3.4d2c fork-run blocker)

**(i) The defect, and the run that surfaced it.** The first end-to-end rehearsal fork run (`test/fork/StagePRunRehearsal.t.sol`, at PB3.4d2b2b) reverted in `setUp` with the Vault's `TokensNotSorted()`. `deploy-miliarium-pool.s.sol`'s `run()` assembles its `TokenConfig[]` in raw config-array order (L69–L77), substituting `_resolveStub(cfg.tokens[i])` slot by slot, and hands `cfg.normalizedWeights` to `create()` unpermuted (L109); the script contains no sort. **(ii) Scope — a production-path defect, not a rehearsal artifact.** The failing surface is `script/pools/deploy-miliarium-pool.s.sol`, the single base script all 26 Miliarium pool deploys inherit, and the stub roster it mis-orders is the same one the PB3.5 Sepolia broadcast consumes. **(iii) Why neither standing gate caught it.** The P10 close gate (`StagePIntegration.t.sol`, 13/13) runs with no `STUB_` key set, so `_resolveStub` is pure passthrough per PB-D20 (i) and pool registration sees the mainnet literals in their authored order — the ordering hazard is structurally invisible on that path. **(iv) The fix — an unconditional ascending sort with lockstep weight permutation.** `run()` sorts the resolved `TokenConfig[]` and the `normalizedWeights[]` together, ascending by resolved token address, immediately before `create()`. The permutation is lockstep and non-negotiable: `normalizedWeights` is a parallel array indexed by slot, so sorting tokens without carrying weights would silently seat one leg's weight on a different token — a mispriced pool that registers cleanly and reverts nothing, strictly worse than the `TokensNotSorted()` it replaces. `tokenType`, `rateProvider` and `paysYieldFees` travel inside the `TokenConfig` struct and permute with it for free. The Quality-Gate loop (L79–L84) is an order-independent sum over `cfg.*` by index, so it stays where it is, reading pre-override config exactly as PB-D20 (i) specifies.

**(v) Why the mainnet path is provably unperturbed.** With no `STUB_` key set `_resolveStub` returns its argument unchanged, so the resolved array IS `cfg.tokens` — already ascending by authorship. A sort applied to an already-sorted sequence is the identity, and the accompanying weight permutation is likewise the identity, so the mainnet and mainnet-fork paths produce byte-identical `create()` arguments before and after this change. The claim is checked rather than asserted: the P10 close gate re-runs at the verification rung and must return 13/13 unchanged. This is also why the sort is unconditional rather than gated on whether an override applied — an always-on no-op is exercised by every existing mainnet-path test, whereas a testnet-only branch would ship logic no standing gate ever executes.

**(vi) Rejected alternatives.** (a) Gating the sort behind a stub-applied predicate — keeps the mainnet path untouched by construction rather than by no-op reasoning, and is marginally easier to argue to an auditor, but confines the sorting logic to the one path with the least coverage; the unconditional form is preferred precisely because the mainnet tests exercise it. (b) Grinding stub addresses via CREATE2 salts so each pool's resolved slots preserve config order — leaves every deploy script untouched and keeps PB-D20 (i) literally true, but reverses the PB-D21 (v) plain-CREATE lock, adds real deploy cost and complexity, and is likely unsatisfiable: tokens recur across pools (svZCHF appears in most of the roster), so a single stub address would have to satisfy every containing pool's ordering simultaneously. (c) Re-authoring the 26 config libraries into a stub-friendly order — the configs mirror canonical mainnet addresses and their order is a property of those addresses, not a free choice; no single order is correct for both the real and the stub roster.

**(vii) The PB-D20 (i) amendment, the ladder, and the gates.** PB-D20 (i)'s standing wording — that the override touches swap ADDRESSES only, while `tokenTypes`, `normalizedWeights`, `paysYieldFees` and the QG re-assertion keep reading pre-override `cfg.*` — is amended here: the override still reads no overridden VALUE into those arrays, but `normalizedWeights` is now REORDERED in lockstep with the tokens it indexes, and the script's L42–L46 NatSpec is corrected to say so at the fix rung. Ladder: d2c1 — the sort plus the NatSpec correction in `deploy-miliarium-pool.s.sol`, `forge build` green. d2c2 — verification in one rung on two gates: the P10 close gate re-run at 13/13 (the mainnet-invariance proof of (v)) and the rehearsal `setUp` clearing all 26 pool deploys. d2c3 — the four post-condition re-assertions in the rehearsal test body, the original PB-D25 (v) d2c content, fork-green. ## PB-D28 — PB-D27 (iv)(1)/(x) amendment: the per-step EOA transaction counts defer from rung e to rung h — the runbook lands with the derivation method and an unpopulated count table (user-adjudicated 2026-07-26; PB3.5e pre-flight blocker)

**(i) The tension.** PB-D27 (iv)(1) requires the runbook to pin the exact EOA transaction count of every broadcast step, derived from a dry run rather than read off the source. PB-D27 (x) places the runbook at rung e and the Sepolia-fork dry run at rung h — four rungs later — and forbids folding h into another rung. As written the two clauses cannot both hold: rung e must either run a dry run early, which is the h rung under another name, or read the counts off the source, which (iv)(1) rejects by name.

**(ii) Resolution — counts defer to h; everything else lands at e.** The two quantities the runbook carries separate cleanly. A step's EOA transaction count is STRUCTURAL: it follows from that script's own CREATE and call sequence and is invariant under the deployer's nonce. A predicted address is NONCE-DEPENDENT, which is precisely why (iv)(2) pins the dry run to the REAL deployer's live nonce immediately before the broadcast. Only the second genuinely needs h. Rung e therefore authors the runbook complete in every other respect and carries a count table that is present, structurally complete down to one row per step, and EMPTY — every count cell reading a literal PENDING-h marker — alongside the derivation method h will execute. Rung h's scope grows by exactly one obligation: derive each count from its own run and populate the table before any broadcast command is issued. h remains the single unrecoverable-immutables gate and is still never folded into another rung.

**(iii) Rejected.** (a) A counting-only simulation inserted ahead of e — a new §8b beat running each script under `forge script` without `--broadcast` against Sepolia on placeholder env. Two steps defeat it: the c1b `BodenseeAddressMismatch` and c2 `HookAddressMismatch` self-asserts revert under any placeholder prediction that is not already the answer, so those counts would be read out of reverted traces rather than clean runs — and the beat produces nothing h does not produce anyway, at the cost of a second network round against a chain whose state the run never advances. (b) Source-derived counts written now and flagged unconfirmed. (iv)(1) rejects source-reading by name and the reason survives the flag: a number on the page is a number an operator can act on, and the failure mode of an undercount is a mis-projected address sealing a vault immutable — the exact unrecoverable class (iv) exists to convert into an abort. An empty cell carrying a PENDING marker cannot be misread as an answer; an unconfirmed number can.
