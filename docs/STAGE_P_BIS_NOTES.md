## PB-D1 — Sepolia is the live-broadcast target (closes the P-D1 live-target deferral; user-adjudicated 2026-07-11)

### PB11 — an em-dash (U+2014) is invalid inside a Solidity string literal — solc 0.8.26 rejects it (invalid-character-in-string-literal, observed as Error 8936); §10's em-dash house style is comments / NatSpec only

Caught at PB2.11b-vi, the face-3 compile of `test/fork/WK18ThinVenuePumpSim.t.sol`: an assertion-message string carried a copy-pasted em-dash and solc 0.8.26 rejected the file at parse with the invalid-character-in-string-literal error (observed as Error 8936). A plain `"..."` string literal admits only printable ASCII plus the defined escape set — U+2014 is representable only in a `unicode"..."` literal or via a `\u2014` escape, neither wanted in a message that compiles into bytecode. §10's em-dash convention is a PROSE house style: it governs comments, NatSpec, docs, and commit messages (UTF-8 to solc, or ignored), but any string that reaches the compiler as a literal — revert reasons, `require` / `assert` / `revert` messages, forge assertion-message arguments, event strings — must be ASCII.

**Rule.** When prose is copied into a Solidity string literal, convert every em-dash to ASCII (`-`, `--`, or reword); after a Solidity edit that pasted prose, grep the diff for U+2014 inside double-quotes before compiling. §10 stops at the quote mark.

## PB-D26 — PB3.4d2c amendment to PB-D20 (i): the stub override must reorder, not only re-address — an unconditional ascending sort with lockstep weight permutation (user-adjudicated 2026-07-25; PB3.4d2c fork-run blocker)

**(i) The defect, and the run that surfaced it.** The first end-to-end rehearsal fork run (`test/fork/StagePRunRehearsal.t.sol`, at PB3.4d2b2b) reverted in `setUp` with the Vault's `TokensNotSorted()`. `deploy-miliarium-pool.s.sol`'s `run()` assembles its `TokenConfig[]` in raw config-array order (L69–L77), substituting `_resolveStub(cfg.tokens[i])` slot by slot, and hands `cfg.normalizedWeights` to `create()` unpermuted (L109); the script contains no sort. **(ii) Scope — a production-path defect, not a rehearsal artifact.** The failing surface is `script/pools/deploy-miliarium-pool.s.sol`, the single base script all 26 Miliarium pool deploys inherit, and the stub roster it mis-orders is the same one the PB3.5 Sepolia broadcast consumes. **(iii) Why neither standing gate caught it.** The P10 close gate (`StagePIntegration.t.sol`, 13/13) runs with no `STUB_` key set, so `_resolveStub` is pure passthrough per PB-D20 (i) and pool registration sees the mainnet literals in their authored order — the ordering hazard is structurally invisible on that path. **(iv) The fix — an unconditional ascending sort with lockstep weight permutation.** `run()` sorts the resolved `TokenConfig[]` and the `normalizedWeights[]` together, ascending by resolved token address, immediately before `create()`. The permutation is lockstep and non-negotiable: `normalizedWeights` is a parallel array indexed by slot, so sorting tokens without carrying weights would silently seat one leg's weight on a different token — a mispriced pool that registers cleanly and reverts nothing, strictly worse than the `TokensNotSorted()` it replaces. `tokenType`, `rateProvider` and `paysYieldFees` travel inside the `TokenConfig` struct and permute with it for free. The Quality-Gate loop (L79–L84) is an order-independent sum over `cfg.*` by index, so it stays where it is, reading pre-override config exactly as PB-D20 (i) specifies.

**(v) Why the mainnet path is provably unperturbed.** With no `STUB_` key set `_resolveStub` returns its argument unchanged, so the resolved array IS `cfg.tokens` — already ascending by authorship. A sort applied to an already-sorted sequence is the identity, and the accompanying weight permutation is likewise the identity, so the mainnet and mainnet-fork paths produce byte-identical `create()` arguments before and after this change. The claim is checked rather than asserted: the P10 close gate re-runs at the verification rung and must return 13/13 unchanged. This is also why the sort is unconditional rather than gated on whether an override applied — an always-on no-op is exercised by every existing mainnet-path test, whereas a testnet-only branch would ship logic no standing gate ever executes.

**(vi) Rejected alternatives.** (a) Gating the sort behind a stub-applied predicate — keeps the mainnet path untouched by construction rather than by no-op reasoning, and is marginally easier to argue to an auditor, but confines the sorting logic to the one path with the least coverage; the unconditional form is preferred precisely because the mainnet tests exercise it. (b) Grinding stub addresses via CREATE2 salts so each pool's resolved slots preserve config order — leaves every deploy script untouched and keeps PB-D20 (i) literally true, but reverses the PB-D21 (v) plain-CREATE lock, adds real deploy cost and complexity, and is likely unsatisfiable: tokens recur across pools (svZCHF appears in most of the roster), so a single stub address would have to satisfy every containing pool's ordering simultaneously. (c) Re-authoring the 26 config libraries into a stub-friendly order — the configs mirror canonical mainnet addresses and their order is a property of those addresses, not a free choice; no single order is correct for both the real and the stub roster.

**(vii) The PB-D20 (i) amendment, the ladder, and the gates.** PB-D20 (i)'s standing wording — that the override touches swap ADDRESSES only, while `tokenTypes`, `normalizedWeights`, `paysYieldFees` and the QG re-assertion keep reading pre-override `cfg.*` — is amended here: the override still reads no overridden VALUE into those arrays, but `normalizedWeights` is now REORDERED in lockstep with the tokens it indexes, and the script's L42–L46 NatSpec is corrected to say so at the fix rung. Ladder: d2c1 — the sort plus the NatSpec correction in `deploy-miliarium-pool.s.sol`, `forge build` green. d2c2 — verification in one rung on two gates: the P10 close gate re-run at 13/13 (the mainnet-invariance proof of (v)) and the rehearsal `setUp` clearing all 26 pool deploys. d2c3 — the four post-condition re-assertions in the rehearsal test body, the original PB-D25 (v) d2c content, fork-green. ## PB-D32 — PB3.5i blocker: the compiled Vault overruns EIP-170 because the toolchain never matched Balancer's — the per-contract optimizer runs and the OpenZeppelin pin both diverge, and the artifact is reproduced against the deployed mainnet runtime as oracle (user-adjudicated 2026-07-27; PB3.5i blocker)

**(iii) The two divergences, measured.** Balancer's deployed artifacts come from hardhat via `pvt/common/hardhat-base-config.ts`, not from their foundry profile, and that config carries per-contract overrides: `Vault.sol` and `VaultExtension.sol` compile at `runs: 500` while the package base is 9999, which is why the non-overridden `VaultAdmin` fits for us and the two overridden contracts are the two that diverge. `VaultFactory.sol` is not overridden, so the 9999 reading taken from its verified Etherscan source at `0xAc27df81663d139072E615855eF9aB0Af3FBD281` and recorded at `foundry.toml` L6 was correct for that contract and wrong only in being generalised to the package. **(iv) The finding beneath the finding — artifact inheritance was never true.** CLAUDE.md §2 states the Vault contracts are byte-identical to audited Balancer V3 code, and `foundry.toml` L11 escalates that to a dependency on byte-level toolchain parity. **(v) Decision — reproduce the audited artifact.** CHOSEN: restore genuine artifact parity, verified rather than asserted. Fitting is a side effect of parity, not a goal beside it.

**(vi) The oracle — a masked byte-comparison, not a size threshold.** Mainnet `0xbA1333333333a1BA1108E8412f11850A5C319bA9` holds the exact bytes being reproduced, so candidate configurations are judged against those bytes rather than against the limit, and a byte match closes runs, `optimizerSteps`, the OpenZeppelin pin and submodule-pin fidelity simultaneously. ## PB-D35 — PB-D27 (iii) amendment: the Sepolia address overlay moves out of `.env` into an explicitly-sourced `.env.sepolia`, because the shared file silently disabled every mainnet fork suite (user-adjudicated 2026-07-28; PB3.5i5)

**(i) The defect.** PB3.5 phase A populated `.env` with the Sepolia overlay — 67 `STUB_` pairs mapping each mainnet token literal to its Sepolia stub, the eight base-layer address projections plus `FEE_CONTROLLER` and a `GENESIS_BLOCK` placeholder, and `SV_ZCHF` / `SUSDS` repointed from their mainnet addresses to stubs. Foundry auto-loads `.env` for every invocation, including `forge test`. PB-D20's override resolver is `vm.envOr("STUB_" + vm.toString(literal), literal)` in `script/pools/deploy-miliarium-pool.s.sol`, mirrored onto the two rate-provider slots of `DeployDerBodensee` per PB-D27 (v), and it activates purely on KEY EXISTENCE — no flag, no opt-in. **(ii) Why no gate caught it.** Nothing ran a mainnet fork suite between phase A at rung h on 2026-07-26 and the PB-D34 work on 2026-07-28. The unit suites are unaffected because they bind no mainnet literals, so 947 tests stayed green throughout and gave no signal. The failure is not detectable by inspection either: `.env` is gitignored, so no diff surfaces it, and the resolver's passthrough default means a populated map looks exactly like an empty one until a literal is dereferenced on-chain. **(iii) The cause.** PB-D27 (iii) amended PB-D21 (v) to thread broadcast addresses through `.env` rather than `vm.setEnv`, correctly, because each `forge script --broadcast` is its own process and `vm.setEnv` mutates only one. That reasoning is sound and stands. What it did not account for is that `.env` is not a broadcast-only channel — every `forge test` invocation loads it too, and the mainnet fork suites depend on exactly the literals the Sepolia overlay overrides. The clause chose a shared file for a purpose that requires an exclusive one.

(b) Manually stripping the Sepolia block from `.env` before each fork run, which is what was done ad hoc this session — unrepeatable discipline, and the thing that fails is silent. (c) Namespacing the stub keys as `SEPOLIA_STUB_`, which requires the same resolver edit as (a) with none of its clarity.

### PB15 — a compiler-configuration surface is not verified until it is measured: a silently-dropped key and a default-looking value are the same error

Caught across PB3.5i1—i3, the EIP-170 investigation. Two failures with one shape. First, foundry drops multi-word `optimizer_details` keys spelled in snake_case SILENTLY — no error, no warning, no diagnostic — and the only observable effect is a compiled artifact hundreds of bytes larger than intended, which nothing in the pipeline inspects; the keys are camelCase, so `jumpdestRemover` is read while `jumpdest_remover` is discarded, and both look equally plausible sitting in a TOML file. Second, `yulDetails.optimizerSteps` reads exactly like solc's own documented default step sequence, and was dismissed as decorative twice on precisely that reasoning — once when first seen in Balancer's Sourcify input, and again when the ablation was being scoped. It was the entire 782-byte answer, and each dismissal downgraded the one suspect that mattered: supplying a value equal to a documented default is NOT equivalent to omitting it.

**Rule.** Treat every compiler-configuration surface as unmeasured until a build artifact confirms it. `forge build --build-info` writes the literal standard-json handed to solc and is the diagnostic that exposes a dropped key; run it in any sub-step that adds, renames or reorders a compiler setting, and diff the emitted settings against what was intended rather than against what was typed. A configuration value that resembles a tool's default is evidence of nothing — establish by ablation whether it is load-bearing, and never downgrade a suspect because its value looks unremarkable. Cross-ref: PB-D33 (ii) for the ablation table that isolated the step sequence, PB-D34 for the profile scoping that followed, and PB-D37 (i) for the same class of unverified claim, there caught by grep rather than by measurement.

## PB-D39 — PB3.5i9 phase 3 blocker: `BODENSEE_SALT` holds a Miliarium Aureum slot number although der Bodensee is not an MA pool, so ixAetheron's slot-02 salt is already occupied in the factory's sender-scoped CREATE3 namespace — slot 02 broadcasts from a second sender, and the salt moves out of the slot space before mainnet (user-adjudicated 2026-07-29; PB3.5i9 phase 3)

**(iv) Ordering, and why getting it wrong is silent.** `setTokenUnderlying` first, then venue and hop wiring, then seed, then `updateEMA`. **(v) Slot 02 `ixAetheron` — seeded, deliberately unpriced — and the pricing graph that carries the rest.** Twenty-four of the twenty-six configs hold svZCHF, and since a Miliarium pool is itself a Leg 2 venue each of those prices its own tokens directly off itself. ## PB-D42 — PB3.8e: PB-D41 (iii)'s blanket WITH_RATE mapping rule would have priced every pool at zero, so svZCHF takes a self-map exception, and the WITH_RATE underlyings — absent from the committed stub map — are derived from live `asset()` reads under a derive-commit-then-assert model (user-adjudicated 2026-07-30; PB3.8e)

**(i) The defect in PB-D41 (iii), caught before any code was built against it.** That clause locked a blanket convention: WITH_RATE stubs map share to underlying stub, STANDARD tokens self-map, AuMM self-maps. The blanket half is wrong for exactly one token, and wrong in the way that produces no error. `DeployStageP.s.sol` L88 and L153 set the `SVZCHF` immutable from `SV_ZCHF`, which is the svZCHF ERC-4626 **share** address rather than any base asset. Mapping that share to a separate ZCHF stub therefore means no token anywhere resolves to `SVZCHF`. The lock was authored, adjudicated and committed at PB3.8a before this surfaced; the correction lands here rather than as a rewrite so the near-miss stays legible.

**(ii) Two faces, one mechanism.** `_venueRatio` resolves every venue token through `tokenToUnderlying` and matches the result against both `base` and `quote` (L315-L320), with `quote` always the `SVZCHF` immutable — so with svZCHF resolving away from that address, `balQuote` is zero at every venue, every venue returns ineligible, and `_directRatio` returns zero for every base. The second face is `_constellationRatio` L234, which takes the `1e18` identity only when `underlying == SVZCHF`: with balances resolving away from the share address svZCHF never takes its own identity either, and attempts to price as a foreign underlying through the same dead venue path. Both faces fail silently — no revert, no event, every `tvl()` returning zero exactly as it does today. The failure is indistinguishable from the empty-oracle state PB-D41 exists to close, which is what makes it worth a lock of its own.

**(iii) The corrected convention, forced by the code rather than chosen.** `test/unit/TVLOracle.t.sol` seeds `_mapToken(SVZCHF, SVZCHF)` at L276, L291, L314 and L345 — every seeding site in the suite — so the self-map is the convention the implementation was written and tested against, and PB-D41 (iii) diverged from it rather than the reverse.

| Class | Mapping |
| --- | --- |
| svZCHF | self-map; the resolved value must equal the `SVZCHF` immutable |
| Other WITH_RATE wrappers | share → underlying stub, per PB-D41 (iii) unchanged |
| STANDARD | self-map, per PB-D41 (iii) unchanged |
| AuMM | self-map, der Bodensee its venue, per PB-D41 (iii) unchanged |

**(iv) The underlyings are not in the committed stub map.** `test-stubs/DeployTestnetStubs.s.sol` L135-L140 deploys an 18-decimal `StubERC20` underlying and a `StubERC4626` over it, then records only the vault under the `STUB_<literal>` key. The underlying addresses — one per WITH_RATE slot, across 87 slot occurrences in all 26 configs — therefore exist only on chain, reachable solely through `asset()` on each live share. Re-running `DeployTestnetStubs` is not an escape and must not be attempted: it CREATEs a fresh roster on every invocation rather than discovering the existing one, so it would orphan the stub addresses the 26 live pools already hold. The runtime NatSpec rejecting ERC-4626 `asset()` introspection binds the oracle's own valuation path and does not bar a one-shot governance-curation read, which is a deliberate off-chain derivation rather than a runtime fallback.

**(v) The same derivation feeds `addHopUnderlying`, not only `setTokenUnderlying`.** PB-D41 (iii) names the PB-D7 hop seeds as "the stub ZCHF and USDS keys" as though they were independent env values. They are not: they are precisely the `asset()` outputs of the svZCHF and sUSDS shares, so one derivation produces both the per-token mapping and the hop roster. Recorded because the wording invites a search for env keys that do not exist, and finding none invites inventing them.

**(vi) Derive-commit-then-assert.** Rung e runs a read-only pass calling `asset()` on each live WITH_RATE share against Sepolia, emits the full token-to-underlying map, and commits it as a reviewable data artifact on the PB-D41 (vi) precedent that deployed state stays reproducible from the repo. The wiring script at rung f then applies the committed table while re-asserting each entry against a live `asset()` read before writing, so drift between the committed artifact and the chain fails closed at wiring time instead of silently writing a wrong mapping. The chain read is thereby a discovery step with a review surface in front of it, never an unreviewed runtime dependency of the wiring script.

**(vii) What PB-D41 keeps.** Every other clause stands unamended: the five-part scope and the PB3.8/PB3.9 genesis split at (ii), the required `addConstellationPool(derBodensee)` and the L12 NatSpec divergence at (iii), the ordering hazard at (iv), the slot 02 disposition and the `ixHelvetia` pricing path at (v), the USD 1,000,000 banded allocation table at (vi), the `normalizedWeights` split at (vii), der Bodensee filling by flow at (viii), the Stage-R gate at (ix), and the keeper at (x). This lock replaces one row of one clause and adds the data-availability model rung e needs.

**(viii) Trigger.** Drafting rung e's derivation required naming what each WITH_RATE stub maps to, which required reading `_venueRatio` rather than the convention — and the convention, read alone, is self-consistent and wrong. Nothing in PB-D41 (iii) is internally contradictory; it fails only against the comparison at L315-L320, three files away. A blanket rule over a typed domain is not verified by being coherent, only by being checked against every consumer of the domain, and the numeraire is a member of the set the rule quantifies over.

### PB16 — a source file outside foundry's configured compile roots is invisible to `forge build`, so a green build is evidence about the graph forge chose to walk and not about that file; the artifact directory under `out/` is the only positive proof it compiled

Caught at PB3.8e1, on the first net-new file placed in `test-stubs/` that nothing imports. `foundry.toml` sets the compile roots to `src`, `test` and `script`, and names `test-stubs/` nowhere; the files already living there carry artifacts only because something inside a configured root reaches them, `test/fork/StagePRunRehearsal.t.sol` importing `DeployTestnetStubs.s.sol` which in turn imports both stub templates, pulling all three into the graph transitively. A file no configured root reaches is never compiled at all, so `forge build` returns green without having read it — and the §8e.1 verify block that used `forge build` as its compile gate therefore proved nothing whatsoever about the only file the sub-step created, while looking like it had. The tell was an absence rather than an error: `ls out/DeriveTokenUnderlyings.s.sol/` reported no such directory while the sibling `out/DeployTestnetStubs.s.sol/` existed, which is what separated "did not compile" from "was never offered to the compiler". The diagnostic generalizes past this one directory and is the same shape as PB15 — there, `--build-info` was the only positive evidence a compiler setting had taken effect; here, an artifact under `out/` is the only positive evidence a given file compiled, and in both cases a passing command was mistaken for a passing check because nobody asked what the command had actually examined. The gate for a file outside the roots is `forge build --contracts <dir>` followed by an `ls` on its artifact directory. Adding the directory to `foundry.toml` is rejected as the fix: PB-D34 measured how much blast radius a compile-config change carries, and these are read-only scripts that are never deployed. The exposure is permanent for `test-stubs/DeriveTokenUnderlyings.s.sol`, since PB-D37's `vm.readDir` completeness assertion in `test/unit/BytecodeSize.t.sol` scans `src/` only and no standing gate will ever cover it.

## PB-D43 — PB3.8e2: hop-roster entries are underlyings, not tokens, so PB-D42 (v) overstated the derivation's hop contribution; svZCHF is structurally ineligible on every chain, raw ZCHF is inert on the genesis roster, and seeding the sUSDS share instead of its underlying silently zeroes slot 06 (user-adjudicated 2026-07-31; PB3.8e2)

**(i) The finding, and a word that means two things.** PB-D42 (v) states that the hop seeds "are precisely the `asset()` outputs of the svZCHF and sUSDS shares". Half of that is impossible: the (iii) self-map short-circuits before the WITH_RATE branch, so `asset()` is never called on svZCHF and its base asset never enters the derived map. svZCHF itself is present in that map, self-mapped; what is absent is the ZCHF-side underlying. The conclusion (v) draws still holds — one derivation feeds both wiring calls — but the mechanism named is wrong, and wrong in the direction that invites a reader to add a hop that cannot work. Disambiguation worth stating once, because the confusion is natural: a valuation hop is the `_twoHopRatio` fallback inside `TVLOracle`, entirely unrelated to a swap route, which is the Router composing a path across pools from off-chain path data and which no oracle wiring configures.

**(ii) The level rule.** A hop-roster entry is an underlying — a value that some token RESOLVES TO under `tokenToUnderlying` — never a token address. Every comparison in the path is on resolved underlyings: `_twoHopRatio` calls `_directRatio(hop, SVZCHF)`, which reaches `_venueRatio` and accumulates `balBase` only where `tokenToUnderlying[token] == base`. An entry that nothing resolves to therefore accumulates a zero base at every venue, returns ineligible, fails the `h2 == 0` gate and is skipped. It does not revert and it emits nothing.

| Candidate seed | Effect |
| --- | --- |
| svZCHF (the numeraire) | Skipped unconditionally at `_twoHopRatio` L287 on every chain; hopping through the numeraire IS the direct path already tried at `_constellationRatio` step 2 |
| Raw ZCHF | Inert on the genesis roster, Sepolia AND mainnet: svZCHF self-maps and no Miliarium config holds raw ZCHF, so nothing resolves to it and `h2` is always zero |
| sUSDS, the ERC-4626 share | TRAP: the share resolves to its own underlying, so nothing resolves to the share; `balBase == 0`, the hop dies silently and slot 06 underprices |
| The sUSDS `asset()` underlying | The live intermediate, and what PB-D7's seed line meant by "USDS" |

**(iii) svZCHF is structurally ineligible, on every chain, and this is not a stub artifact.** `TVLOracle.sol` L287 reads `if (hop == underlying || hop == SVZCHF) continue;`. The exclusion is unconditional and has nothing to do with self-mapping or with stubs — seed the real svZCHF on mainnet and the loop skips it identically. This does NOT mean svZCHF liquidity is ignored: a svZCHF balance in the pool being valued contributes through the `_constellationRatio` L234 identity at a 1e18 ratio, and most pools price their non-numeraire legs directly because they hold svZCHF themselves and are Leg 2 venues. The two roles are separate and only the hop role is excluded.

**(iv) Raw ZCHF is inert on mainnet, not only on Sepolia.** The only ZCHF-named constants across all 26 configs are `SVZCHF` and `SVZCHF_RATE_PROVIDER`; no pool holds raw ZCHF. Combined with the svZCHF self-map, nothing resolves to ZCHF on either chain, so a ZCHF entry costs one loop iteration and one `_directRatio` call returning zero. Harmless but dead on the genesis roster, and it must not be added on the assumption that Sepolia is the special case; (vii) governs the case where a later permissionless pool makes it live.

**(v) The trap, stated concretely because it is the one that costs something.** Slot 06 `ixLibertas` is the only pool on the genesis roster that needs a hop at all — it holds no svZCHF (four sUSDS references, zero svZCHF) while 24 of the 26 price directly and slot 02 `ixAetheron` is unpriced by design per PB-D41 (v). Its entire valuation path is `USD stables → the sUSDS underlying → svZCHF`, with `ixHelvetia` supplying both legs as a sUSDS-plus-svZCHF venue. Seeding the sUSDS share rather than its underlying fails at `h2` — `_directRatio(share, SVZCHF)` finds no token resolving to the share, returns zero, and the loop continues before `h1` is ever computed — and the observable result is a pool reporting a fraction of its true TVL with no error anywhere, the same silent-zero class as the PB-D42 (iii) defect, one clause over.

**(vi) The roster, and the Stage-R marker.** For this deployment the hop roster is exactly one entry: the sUSDS-derived underlying, `0xCc72810e4A91D2BDba70B380C9c41327D0E63169` on Sepolia, confirmed by the PB3.8e2 derivation where sUSDS resolves away from itself. Rung f seeds that and nothing else; (vii) governs later growth. The level rule is chain-independent and the mainnet wiring will meet it identically, so it is named here as a Stage-R gate and registered as RB-012, whose hardening class is assigned when the row lands — the existing Environment-scope isolation class is a poor fit for what is a typed-domain level error. PB-D7's text is left intact as the historical disposition and cited rather than amended, per the house pattern that superseded locks stay readable; its "a 2-hop path through ZCHF or sUSDS" phrasing, inherited from FINDINGS L1119, is the origin of both errors this lock corrects.

**(vii) Permissionless pools, and why one entry is a roster property rather than an invariant.** Pool creation is permissionless from block 0 per `08_bootstrap.md` while `MiliariumRegistry.SLOT_COUNT` is fixed at 28, so a pool outside that set never enters the Leg 2 enumeration and becomes a pricing venue only if governance appends it through `addConstellationPool`. That is a valuation-topology constraint and NOT a second-class emission status: `activateGauge` carries no access modifier beyond its svZCHF anti-spam fee, `EmissionDistributor` L481-L485 scores every gauged pool, and `_alphaF3` L444-L448 makes the difference purely temporal — a non-Miliarium pool earns zero until month 10, ramps to year 1, and from year 1 onward runs the identical score path with MA membership conferring nothing at all. The 28 slots are F-3 bootstrap weighting, not an entitlement gate. What the oracle does require is that a pool's tokens resolve: a pool built from already-admitted ERC-4626 classes inherits their existing mappings and needs no governance act, while a pool introducing a genuinely novel underlying reads a zero contribution for that leg, and because `GaugeEligibility.TVL_FLOOR_SVZCHF` is `10_000e18` it fails `TVLFloorNotMet` and cannot gauge until someone maps it — so oracle mapping must keep pace with class admission, a two-authority coupling recorded separately as RB-013 rather than absorbed here. All three rosters are governance-curated, append-only and carry no removal primitive, `addHopUnderlying` reverting `AlreadyAdded` on a duplicate. The single entry in (vi) is therefore a property of the genesis 26 and not a permanent invariant: a later pool may make a currently inert underlying live, raw ZCHF included, superseding (iv) for that underlying through the same governance acts. Nothing here forbids that; what it forbids is seeding an entry that nothing resolves to yet.

## PB-D44 — PB3.8e3: the derived map commits as a Solidity library under `script/config/`, transcribed literally from the derivation log rather than re-keyed to named constants, and bound to Sepolia by name, by NatSpec and by a rung-f chain assertion (user-adjudicated 2026-07-31; PB3.8e3)

**(i) What PB-D42 (vi) settled, and the gap it left.** PB-D42 (vi) locked derive-commit-then-assert: a read-only `asset()` pass emits the map, the map commits as a reviewable artifact on the PB-D41 (vi) precedent that deployed state stays reproducible from the repo, and rung f re-asserts each entry against a live read before writing, so drift between artifact and chain fails closed at wiring time. What it did not fix is the artifact's FORM, and form is load-bearing in two independent directions: it decides whether a 120-address transcription can be verified mechanically rather than by eye, and it decides whether a Sepolia table can be mistaken for a mainnet one. Half the answer is already in the tree — `test-stubs/DeriveTokenUnderlyings.s.sol` at `d763273` emits its map as Solidity assignment statements and names `script/config/SepoliaTokenUnderlyings.sol` in its own header comment — so this lock records the remainder rather than reopening what the script already decided.

**(ii) A library under `script/config/`, taking the `GaugeGenesisManifest` skeleton and deliberately refusing its constant layer.** The sibling `script/config/GaugeGenesisManifest.sol` is the house precedent for a committed address table consumed by a deploy script: SPDX identifier, `pragma solidity ^0.8.26`, a NatSpec block carrying provenance, a `library` rather than a contract, a count constant, and an `internal pure` accessor assigning into index-aligned arrays. `SepoliaTokenUnderlyings` follows all of that except the named `address internal constant` layer, and the refusal is not stylistic. `GaugeGenesisManifest`'s 11 entries are mainnet tokens with real identities — `SVZCHF`, `SUSDS`, `WAETHUSDC` — so a name carries meaning and a reviewer can check the name against the address independently. The 60 Sepolia entries are freshly CREATEd stubs whose only identity is the address itself; any name would have to be invented at transcription time, and an invented name is precisely the memory oracle the §8e.1 transcription rule bans, because a reviewer would then be checking Cursor's output against Claude Code's naming rather than against the chain. Raw hex literals keep the artifact's sole authority the derivation log.

**(iii) The accessor, and why the array locals are named `t` and `u`.** The library exposes `PAIR_COUNT` at 60 and one `internal pure` function returning two index-aligned `address[] memory` arrays, tokens first and underlyings second, mirroring the `GaugeGenesisManifest.genesis()` shape so rung f consumes a familiar surface. The locals are named `t` and `u` rather than `tokens` and `underlyings`, against normal house register, because the verification strategy demands it: 120 hex addresses cannot be audited by eye, so the audit is a `diff` of the saved assignment block against `test-stubs/pb38e2-derived.log`, and every character the library adds to those lines is one more transform the auditor must trust rather than read. With `t` and `u` the only difference between artifact and log is leading whitespace, normalized symmetrically on both sides by a single obvious substitution. Meaning lives in the NatSpec return documentation, where it costs the diff nothing.

**(iv) The table is Sepolia-bound, and that is an RB-010 shape.** A committed address table under `script/config/`, sitting beside `mainnet-token-decimals.env`, is exactly the configuration-applies-to-the-wrong-chain hazard RB-010 records, and these 60 entries are Sepolia stubs holding no code on mainnet. Three independent guards, because a file name alone is discipline rather than enforcement: the library is named `SepoliaTokenUnderlyings` so no call site reads as chain-neutral, its NatSpec states the chain and the deriving commit in the first lines, and rung f asserts chain identity before writing anything. Per PB-D36 the active environment already carries the `AUMM_ENV_CHAIN` marker and fails CLOSED on absence, so the assertion has a marker available to read.

**(v) Regeneration is safe here and is NOT safe one script over.** `DeriveTokenUnderlyings` is read-only — it calls `asset()` and emits — so re-running it against Sepolia costs nothing and reproduces the map byte-identically, confirmed across two separate invocations at e2 returning identical counts and pair values. That is the exact opposite of `DeployTestnetStubs`, which PB-D42 records as must-not-be-re-run because it CREATEs a fresh roster on every invocation and would orphan the stub addresses the 26 pools already hold. The two scripts sit in the same directory and the distinction is invisible from their names, so it is stated plainly here: derive freely, deploy never. Capture is by shell redirect rather than by `tee`, a `tee` into a pipe having truncated the log once already on an interrupted second invocation.

**(vi) What this does not lock.** Rung f's assertion mechanics stay open to rung f's own drafting — whether the chain check reads `AUMM_ENV_CHAIN`, `block.chainid`, or both, and whether the per-entry live re-assert PB-D42 (vi) requires reverts on first mismatch or accumulates and reports at the end. So does the RB-012 membership check on `addHopUnderlying`, which is a Stage-R hardening item rather than a rung-f obligation. The map's CONTENT is closed: 60 pairs, 47 self-mapping and 13 resolving away, those 13 pairwise distinct with no duplicate underlying among them, svZCHF self-mapping per PB-D42 (iii), AuMM self-mapping, and the single sUSDS-derived hop underlying of PB-D43 (vi) present as the resolution of index 0.

## PB-D45 — PB3.8f: the wiring script verifies all 60 entries read-only before writing any, asserts Sepolia by `block.chainid` rather than by the environment marker, and guards both append-only setters against the partial-run revert that PB3.5 makes a live risk (user-adjudicated 2026-07-31; PB3.8f)

**(i) What PB-D44 (vi) left open, and one hazard neither lock saw.** PB-D44 (vi) deferred three things to rung f's own drafting: whether the chain check reads `AUMM_ENV_CHAIN`, `block.chainid`, or both, and whether the per-entry live re-assert PB-D42 (vi) requires reverts on first mismatch or accumulates and reports. Pre-flight closed those and surfaced a fourth that no lock records: the sequence is not safely re-runnable. `addHopUnderlying` L188 and `addConstellationPool` L168 each revert `AlreadyAdded` on a duplicate, so a run that stalls after the roster calls cannot simply be re-invoked — it reverts rather than resuming. `setTokenUnderlying` is exempt, being a plain overwriting setter, so the hazard is confined to the two append-only surfaces, but at roughly 62 transactions against a chain where PB3.5 already produced one partial sequence, resumability is a property to design in rather than to discover.

**(ii) Chain identity asserts on `block.chainid`, not on the environment marker.** The script requires `block.chainid == 11155111` and reverts otherwise, before it reads a single address or sends a single transaction. `AUMM_ENV_CHAIN` is deliberately NOT the mechanism: PB-D36's marker exists to tell an operator which of the three env files is currently active, a question about the working copy rather than about the chain being written to, and it is answered off-chain where a stale or hand-edited value is indistinguishable from a true one. `block.chainid` is read from the node actually executing the call, cannot disagree with the chain it names, needs no new environment key, and behaves identically inside the rung-h mainnet-fork rehearsal, where it fails closed for exactly the right reason. Pre-flight confirms this establishes a pattern rather than following one — `AUMM_ENV_CHAIN` has zero readers under `script/` and `block.chainid` appears nowhere in the directory — so the assertion is written as a named guard the rung-g seeding script can reuse rather than as an inline literal.

**(iii) Two phases, verify-all then write-all, and the assert rule is forced by the data rather than chosen.** Phase one walks all 60 pairs from `script/config/SepoliaTokenUnderlyings.sol` performing only reads, accumulating every mismatch rather than reverting on the first, and aborts with the total count if any entry fails — so an operator sees the whole picture in one run instead of discovering 13 problems across 13 round-trips, and no state has changed when they do. Phase two writes only if phase one is clean. The per-entry rule follows from PB-D42's convention rather than from preference: where `t != u` the entry is a WITH_RATE wrapper and `IERC4626(t).asset()` must equal `u` exactly, the live read PB-D42 (vi) requires; where `t == u` the entry is a self-map and there is nothing to dereference, so the assertion is structural. The 47-and-13 split is not a proxy for ERC-4626-ness and must not be implemented as one: svZCHF is a genuine ERC-4626 share that self-maps by the PB-D42 (iii) exception, so a rule reading "self-mapped means not a vault" would fail on the numeraire and take the whole run down.

**(iv) Both append-only setters are read-before-call, and the roster calls are idempotent by construction.** Before `addHopUnderlying` the script reads `isHopUnderlying[underlying]` and skips when already true; before `addConstellationPool` it reads `isInGovernanceRoster[pool]` and skips likewise. Both mappings are public reads on the live oracle, so the guard costs one call each and converts the whole sequence into something an operator can re-run after any interruption without reasoning about how far the previous attempt reached. `setTokenUnderlying` needs no guard to be safe, but the script skips entries already holding the intended value anyway — at 60 writes the saved gas is real, and on a chain where the deployer's balance is the live constraint, a resumed run that re-sends only what is missing is the difference between finishing and stalling again.

**(v) Ordering is enforced in code, not left to the operator, because the failure is silent.** All 60 `setTokenUnderlying` writes precede `addConstellationPool(derBodensee)` within a single script run. This is PB-D41 (iii)'s ordering rule and the mechanism is now confirmed at source: `addConstellationPool` L171—L177 reads the pool's tokens and appends the pool to `_underlyingToPools` only under those whose `tokenToUnderlying` already resolves non-zero, skipping the rest with no revert and no event, exactly as its own NatSpec warns at L198 and L163. Der Bodensee holds AuMM and svZCHF, both of which sit in the 60, so calling the roster first would index the pool under nothing and leave a venue that exists on chain but is invisible to `_directRatio` — the same silent-omission class as PB-D42 (iii) and PB-D43 (v), and undetectable afterward without reading the reverse map. Sequencing them in one script removes the possibility rather than documenting it.

**(vi) What this does not lock.** Whether the 62 transactions broadcast as one `forge script` invocation or split into tranches is a rung-i operational question that depends on the deployer's balance at broadcast time, not a property of the script, which stays a single resumable entry point either way. The pool seeding of PB-D41 (vi) is rung g and unaffected. The RB-012 membership assertion on `addHopUnderlying` remains a Stage-R hardening item: rung f seeds one entry it has already proven correct by derivation, so adding the general guard here would be building the backport rather than the wiring. Whether `vaultExplorer.getPoolTokens(derBodensee)` behaves on a registered-but-uninitialized pool — der Bodensee's dust `initialize` being deferred to PB3.9 behind `GENESIS_BLOCK` per PB-D41 and RB-011 — is a rung-h fork-rehearsal question, and the first thing that rehearsal should answer.

## PB-D46 — PB3.8g: every existing pool initialization uses a callback pattern that cannot broadcast, so seeding routes through the Aureum Router; WITH_RATE legs fund by real deposit rather than bare share mint; amounts derive from allocation times registered weights at one dollar per token (user-adjudicated 2026-07-31; PB3.8g)

**(i) The blocker, and why every rehearsal so far would have passed anyway.** Every pool initialization in the tree drives `vault.unlock(abi.encodeCall(this._initializePoolCallback, ...))` — `test/fork/StageGIntegration.t.sol` L363 and `test/fork/StagePRunRehearsal.t.sol` L464 — where the callback target is the harness contract itself. That works in a fork test because the harness is real deployed code at a real address. Under `forge script --broadcast` it cannot work at all: `run()` executes as a simulation that emits transactions from the EOA, the script contract is never deployed to the chain, and the Vault would re-enter an address holding no code. The failure mode is the PB-D31 shape exactly — a rehearsal that replays the pattern in-process passes, and the live broadcast fails at the first pool, after gas has been spent on minting and approvals. Naming it here is the whole point of writing the lock before the script.

**(ii) Initialization goes through the Aureum Router, and D32 does not forbid it.** `Router.initialize(pool, tokens, exactAmountsIn, minBptAmountOut, wethIsEth, userData)` performs the unlock internally and passes `sender: msg.sender`, so it is an ordinary EOA-to-contract call that broadcasts like any other. D32's rule that fork initialization uses `Vault.unlock` with no Router and no Permit2 is not being reversed: that rule existed because the mainnet Router is bound to the mainnet Vault and could not serve an Aureum pool, and PB3.3 has since deployed an Aureum Router bound to the Aureum Vault, which is the object D32 lacked. The Router pulls tokens through Permit2 rather than by direct `transferFrom` — `RouterCommon` L309 calls `_permit2.transferFrom(sender, address(_vault), amountIn.toUint160(), address(tokenIn))` — so every token requires the two-step allowance, an ERC-20 approval to the canonical Permit2 and a Permit2 allowance to the Router carrying a `uint160` amount and a `uint48` expiry. `minBptAmountOut` is zero and `wethIsEth` is false: no leg is native ETH, and initialization admits exactly one winner per pool, so there is no slippage surface for a bound to protect.

**(iii) WITH_RATE legs fund by depositing real underlying, not by minting bare shares.** `StubERC4626` exposes both a permissionless `mint(address,uint256)` at L84 and a genuine `deposit(uint256,address)` at L64, and the cheap path is tempting: one transaction instead of three. It is rejected. `totalAssets()` L33 returns `_ASSET.balanceOf(address(this))`, so a directly minted share is entirely unbacked, and `withdraw` L79 performs a real `safeTransfer` of underlying and therefore reverts for any holder attempting to unwrap. Valuation would not notice — `previewRedeem` is `pure` at L58 and `ERC4626RateProvider.getRate()` reads `1e18` either way, as that function's own comment records — which is precisely what makes the shortcut dangerous: it is invisible to the oracle and visible to a user. PB-D41's trigger was that the frontend is the de facto pre-mainnet marketing artifact, and a share that cannot be redeemed is the kind of thing that surfaces there rather than in a test. The cost of correctness is small and was measured rather than assumed: 13 WITH_RATE tokens at two extra transactions each is roughly 26 transactions, on the order of 1.3 million gas or about 0.0013 SepETH at observed prices, against a spine already estimated near 0.39.

**(iv) Amounts derive from allocation times weight at one dollar per token, in the pool's registered order.** PB-D41 (vii) converts a pool's dollar allocation to per-token amounts strictly by `normalizedWeights` and then to raw units by each stub's decimals, and it names no price step because there is none: every token is notionally one dollar, which PB-D41 (vi) states outright when it calls the budget accounting TVL rather than an oracle claim. The arithmetic is internally consistent — with `balance_i = allocation * weight_i` every leg's `balance_i / weight_i` equals the same allocation, so all legs price at parity, which is the only coherent choice for stubs carrying no feed. Two implementation constraints follow. Token order and weights are read from the Vault's registered pool data rather than from the config library, because PB-D26 caught exactly this class when tokens were sorted without their weights and a mispriced pool registered cleanly. Decimals are read live per token through `decimals()` rather than taken from a committed table, since the stubs were deployed at real fork decimals and a live read cannot drift from the chain it is about to write to.

**(v) The allocation table commits as a slot-keyed library, and pool addresses resolve through the existing per-slot environment keys.** The PB-D41 (vi) table becomes a committed Solidity library under `script/config/`, following the PB-D44 form for the same reasons — reviewable, diff-verifiable, and reproducible from the repo. It is keyed by Miliarium slot, carrying the 26 seeded slots: 01 through 03, 05, 06, and 08 through 28, with 04 `ixViatica` and 07 `ixCambio` absent per their M-D7 deferral. Slot keying forces how pools resolve: `IMiliariumRegistry` enumerates densely through `miliariumPoolsCount()` and `miliariumPoolAt(index)`, so an index carries no slot identity and cannot be joined to a slot-keyed table without reconstructing the mapping by hand. The script therefore resolves each pool through the existing `MILIARIUM_POOL_NN` environment keys, building the key name in a loop from the table's own slot numbers rather than hardcoding 26 reads. Unlike the token map this table is authored rather than derived, so its gate is the arithmetic identity rather than a diff: the six band totals sum to exactly 1,000,000, asserted in the script rather than trusted.

**(vi) One idempotent script, guarded at every step, broadcast by the deployer rather than by governance.** The user-adjudicated shape is a single script that mints, approves and initializes, with each step preceded by the on-chain read that makes it skippable: sufficient balance skips the mint, sufficient allowance skips both approvals, and `isPoolInitialized(pool)` skips a pool already seeded. This inherits the PB-D45 (iv) property that a run interrupted by exhausted funds is resumed by topping up and re-running, re-sending only what is missing, and it composes with forge's own `--resume` rather than competing with it. The broadcaster differs from rung f and the difference is load-bearing: `setTokenUnderlying` is `onlyGovernance` so rung f broadcasts as the multisig, while initialization is permissionless and its caller becomes the pool's first LP holding its BPT, so rung g broadcasts as the deployer EOA. The `block.chainid` guard of PB-D45 (ii) is reused unchanged and fires before any read or send.

**(vii) What this does not lock.** The EMA bootstrap of PB-D41 is rung j and untouched here, as is the standing keeper of rung k, which runs on its own funded EOA and never the canonical deployer whose nonce sequence backs the committed address projections per PB-D39 (vi). Whether the seeding script and the rung-f wiring script share a chain-guard helper or each carry their own is left to drafting, the guard being four lines either way. Der Bodensee takes no part in rung g: it is 40 percent AuMM, AuMM supply is zero until `GENESIS_BLOCK`, and its dust initialization is PB3.9 behind that gate per PB-D41 (viii) and RB-011. Whether `vaultExplorer.getPoolTokens` behaves on a registered-but-uninitialized pool remains the first question rung h answers, and it now bears on rung f and rung g alike.

## PB-D47 — PB3.8h: the rung-h dry run seeded 21 of 26 and then hit a pool that can never be initialized; a token that is its own rate provider collided with the stub map's single namespace, and the provider it needed was deployed but never recorded (user-adjudicated 2026-08-01; PB3.8h)

**(i) What the dry run bought, at zero cost.** `forge script` against live Sepolia without `--broadcast` seeded 21 pools in simulation — slots 17, 10, 11, 18, 27, 22, 24, 08, 19, 20, 25, 21, 23, 14, 28, 26, 09, 06, 05, 15 and 03 — and then reverted `FailedCall()` at slot 02 `ixAetheron`. Everything PB-D46 fixed held under real state: Router-routed initialization, the Permit2 two-step allowance, backed `deposit` funding for share legs, the idempotency guards visibly skipping allowances already at maximum, registered token order with lockstep weights, and decimals of 6, 8 and 18 all computing correctly, including slot 06's seven-token pool. No gas was spent to learn any of it, and slots 12, 13, 16 and 01 remain untested only because the revert halted the loop before them.

**(ii) The root cause is a namespace collision, not a missing contract.** `script/pools/configs/02_ixAetheron.s.sol` L45 declares `WEETH_RATE_PROVIDER = WEETH` — a self-rate-providing token, correct and unremarkable on mainnet, where real weETH implements `getRate()` itself. `DeployTestnetStubs._processConfig` L117—L129 then runs `_ensureWithRate(token)` first, which records `STUB_<token>` as the stub vault at L140; the rate-provider branch at L122 guards on `stubOf[rp] == address(0)` to avoid double-recording a shared provider, finds that slot already occupied by the token's own entry because `rp == token`, and skips its `_record`. Both the token map and the rate-provider map live in one `STUB_` namespace, so a token that is its own provider shadows itself. `_resolveRateProvider` at `script/pools/deploy-miliarium-pool.s.sol` L57—L63 then resolved the provider literal through `_resolveStub` to the stub vault, and slot 02 registered with its rate provider set to one of its own tokens.

**(iii) Why that is terminal for slot 02, and why only slot 02.** Rate providers are sealed at registration: `VaultExtension` L217—L221 writes `TokenInfo` once, and no setter exists anywhere in `VaultExtension`, `VaultAdmin`, `Vault` or any vault interface. The stub at that address cannot be upgraded either. The pool at `0xD259F35a138383Ac8b545F06C5eBADcA3f6a2890` therefore cannot hold liquidity under any wiring, governance act or re-run, and must be redeployed. The blast radius is exactly one line in twenty-six config files — `grep` over every config returns weETH's declaration alone — and weETH appears in no other pool, so nothing already seeded is exposed and the four untested slots carry no instance of the pattern.

**(iv) The provider was never missing; it was unrecorded.** `DeployTestnetStubs` L137 constructs a real `ERC4626RateProvider` for every WITH_RATE stub, weETH included, so the contract slot 02 needed was deployed in the original stub run and then discarded when the script ended without emitting it. It was recovered by arithmetic rather than redeployed: the three contracts per WITH_RATE token are consecutive plain CREATEs, the weETH stub vault sits at deployer nonce 13, and nonce 14 holds `0x4a4EA25a6359852d4e47031Fc1316F3aE13de0a3` — 505 bytes of code, `getRate()` returning exactly `1e18`, and `wrappedToken()` returning `0x3294eB8582279311D4900D18fa88726Abc9aa5E2`, the very stub registered as slot 02's second token. That last read is what makes it provably THE weETH provider rather than merely a working one, which matters because every stub is fixed 1:1 and a wrong provider would price identically today and diverge silently later. The fix costs zero new contracts.

**(v) Borrowing Balancer's mainnet providers cannot serve a stub chain, and on mainnet we already do.** A rate provider is a thin wrapper whose entire value is what it points at, sealed in its immutables. A mainnet provider's address holds no code on Sepolia, which is the exact failure this lock records; redeploying its bytecode does not rescue it, because it would read mainnet weETH, which does not exist on Sepolia; and copying a creation-code hash transplants no dependencies. The only thing that can price a Sepolia stub is a provider constructed over that stub. For mainnet the instinct is already the design — the configs encode real provider addresses verbatim, `RETH_RATE_PROVIDER` among them, and Stage R uses them directly. Stub substitution is a Sepolia-only overlay.

**(vi) Rate providers are optional per token, and the requirement here is self-imposed.** `VaultTypes.sol` L199—L200 and `VaultExtension` L223—L233 are explicit: a STANDARD token must carry a zero provider and `paysYieldFees` false, a WITH_RATE token must carry a non-zero provider, and anything else reverts `InvalidTokenConfiguration()`. Most Balancer tokens are STANDARD with no provider at all, and every one of the 26 pools already has such legs. So the provider is mandatory only because the config declares weETH WITH_RATE, and registering it STANDARD on the testnet was a genuine alternative — numerically identical at a fixed 1:1 stub, and still clear of the script's 52% quality bar at 70% rather than 84%. It is REJECTED because it would edit `tokenTypes` in a config file that mainnet also reads, mutating mainnet source to work around a testnet defect — the precise thing the deployment record praises avoiding on the salt collision. The alternative of teaching the resolver to rewrite a token's TYPE under substitution is a far more surprising rule than teaching it to substitute a provider.

**(vii) The fixes, and the redeploy's own constraint.** Two code changes, neither touching mainnet source. Rate-provider keys move to their own namespace so a token and a provider sharing a literal can never shadow each other, which retires the collision class rather than patching the guard that exposed it; `DeployTestnetStubs` is fixed forward-only and is NOT re-run, since PB-D42 records that re-running mints a fresh roster and orphans every address the 26 pools already hold. And `_resolveRateProvider` probes `getRate()` before returning, failing loudly when a resolved provider cannot answer — the generalizable guard, and the one that would have caught this at deploy time rather than at seeding. The redeploy carries a constraint of its own: `BasePoolFactory._computeFinalSalt` hashes `msg.sender` with the chain and salt, slot 02's salt is occupied for the second EOA `0xbF7BE08923CB549721CDba6516e0Cc9ae0f68A8e` exactly as it was for the canonical deployer under `BODENSEE_SALT`, so a third funded sender is required and the slot-derived salt of E-D20 stays unmutated. The dead pool stays on chain and is labelled abandoned-in-place in the deployment record per section 8f.

**(viii) The wider gap this exposes, and the ladder.** `DeployTestnetStubs` records fewer contracts than it deploys, and the same gap has now produced two failures with opposite endings: the WITH_RATE underlyings went unrecorded and were recoverable, because a token exposes `asset()` and PB-D42 built rung e's derivation on exactly that probe; weETH's provider went unrecorded and was NOT recoverable that way, because no on-chain call from a token reveals its rate provider, leaving nonce arithmetic as the only route back. The Sepolia deployment record already flags the underlying condition as an open item — the 87 stub addresses live only in a gitignored file and are unversioned — and this is the first time that gap cost something. Ladder: h1 this lock; h2 the plan mirror; h3 the register row; h4 the provider-namespace fix in the stub script, forward-only; h5 the resolver namespace lookup plus the `getRate()` probe; h6 the recovered address committed to the deployment record and wired into the operator environment; h7 the third sender funded and slot 02 redeployed; h8 the dry run re-run for a clean 26 and a real gas figure; h9 the broadcast.
