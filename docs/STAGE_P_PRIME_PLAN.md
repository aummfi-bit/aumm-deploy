## Stage scope

Stage P-prime exists to consume the seam-1 audit output before Stage Q engages a firm: the 82 confirmed findings reduce to 51 distinct root causes (plus two composites that own no root of their own), every one of which exits **Fixed, Accepted-risk-with-evidence, or False-positive-with-refutation**, and the proof of closure is a second seam-1 run against the patched commit rather than a ledger assertion. The stage is inserted after P-bis because the audit ran against P-bis's tip while P-bis is still open (PB3.9 and PB5 are not done); it is named P-prime by the user's choice and the name is not re-litigated here. Adjudications precede builds (PP-D4, the §12 ambiguity-gate): Workstream A locks a verdict and a fix intent per root cause in the queue file before any Workstream-B rung opens, and every rung that touches a fix-ordering constraint (§"Fix sequencing") cites the PP-D entry that governs it.

Three things distinguish this stage from P-bis's workstream A. First, the input is external: the adjudications are of findings the project did not raise, several of which overturn the project's own earlier dispositions (F-01 and F-05 shown incomplete, F-15's Accepted-risk REOPENED by G39 §5, F-16 shown incomplete on two independent grounds, F-22's accepted residual shown to be a latch rather than a residual per G36 correction 4). Second, the fixes interact: the report's "Defects that only bite once you fix something else" names four pairs, this plan finds sixteen more, and a rung landed out of order introduces a defect that does not exist today. Third, the exit is a measurement: P10's fork validation proved deploy wiring by running it; PP6 proves remediation by re-running the audit.

## Fix sequencing

Some fixes create defects that do not exist today. The report's "Defects that only bite once you fix something else" names four pairs; the validator notes, G11, G14, G16 and the dependency structure of the contracts themselves supply sixteen more. Every pair below is an ordering constraint with its own PP-D entry, and a Workstream-B rung that touches either side of a pair cites that entry in its prompt's `Must match`. The rule the constraints share is the report's: treat every accepted fix as a query — *where else does this shape occur, and what was relying on the defect?*

**The pairs the report names (carried, with the companion each fix requires):**

1. **G.3 ⇒ `GaugeChallenge` re-check** (PP-D9). "Miliarium pools cannot be gauge-challenged" is true in code only because `proposeGaugeChallenge`'s propose-time `slotOf(target) == 0` (`AureumGovernance.sol:229`) can never be falsified — the only `replaceSlot` caller (`:432`) immediately calls `registerGaugeFromComposition` (`:433`), which rejects an `Active` pool (`GaugeRegistry.sol:170`). Letting the composition branch tolerate an already-`Active` candidate (the fix that closes the 100-svZCHF poison) makes an `Active` pool seatable, falsifies that premise, and lets a banked simple-majority `GaugeChallenge` terminally revoke a Miliarium pool — the refuted hypothesis promoted to a live High. The `GaugeChallenge` branch at `:426-427` gains an execute-time `SLOT_REGISTRY.slotOf(p.targetPool) == 0` re-check in the SAME rung, with a comment at both sites recording the coupling.
2. **E.2 ⇒ E.4 first** (PP-D13). Restoring a reachable caller to the fee controller's withdrawals makes `routeYieldFeeToHook`'s missing ledger debit live in the same transaction, and that function is the most attractive route to reach for because it sends money to der Bodensee. The debit lands first or in the same change.
3. **E.3 ⇒ A.3 first** (PP-D13). The helper's exact reserve-delta equality also fails under any non-zero aggregate yield fee (`PoolDataLib.sol:77-89` debits accrued yield inside `addLiquidity` while the helper reads the stored pre-fee balance). Switching the yield skim on before the helper is on a strict rise bricks every `propose*` at the first donation after rate growth. A.3 lands before E.3 is even proposed.

**The pairs this plan adds:**

5. **E.6's cursor fix ⇒ `integratedSkim` O(1) first** (PP-D33). Returning from `_accrueGlobal` without advancing `lastAccrualBlock` is correct only once `integratedSkim` no longer walks one epoch per 14 days spanned; otherwise the fix trades a forfeiture for an unbounded catch-up cost on the first user to trigger it. 7. **B.1's denominator redesign ⇒ INV-1 re-adjudication** (PP-D14). The denominator-inflation attack (`poking-dormant-holders-…`) was INVALIDATED on INV-1: `getPastTotalSupply(b) == Σ getPastVotes(v, b)`, because `poke` pushes both traces in one transaction, so the mechanism enfranchises exactly the weight it adds. ## Exit gate

PP6 is the stage's proof in the sense P10's fork validation was P's: the claim "the seam-1 findings are closed" is not asserted from the ledger, it is measured by the instrument that produced them. Three properties make the measurement honest, and each is a PP-D: the harness is pinned (PP-D39) so the delta attributes to the target; the configuration is byte-identical to the first run plus a corrections file (PP-D38, PP1.3) so the second run cannot re-derive what the first already refuted; and the acceptance criterion is stated before the run (PP-D7) so the delta is judged against a rule rather than read for comfort. What the gate cannot prove is stated too: a second run by the same class of tool has the same blind spots (the report's own §secmethod names six author-validated findings and a self-validation that missed two duplicates), so PP6 establishes that the harness no longer finds what it found, not that nothing remains — Stage Q's firm is the independent instrument, and it receives the first report, the queue, and the delta.
